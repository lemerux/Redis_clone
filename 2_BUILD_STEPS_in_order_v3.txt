CHANGES IN THIS REVISION (v3)
-----------------------------
  - jemalloc is the memory allocator from the very first working build. glibc
    malloc stays buildable (CMake option ALLOCATOR) for comparison only.
  - New Step 0B: jemalloc integration, startup self-check, AllocStats, and a
    standalone allocator micro-benchmark with an A/B runner script.
  - New Step 7B: allocator A/B memory checkpoint (bytes per key, RSS,
    fragmentation for every data type, plus a churn test).
  - Allocator A/B measurements added to Steps 3, 5, 11 and 12.
  - New Step 13A: the full jemalloc vs glibc benchmark (workloads, metrics,
    fairness rules, tuning sweep, statistics, report). Original Step 13
    content is kept as 13B.
  - Step 15 (README, CI) updated: allocator comparison section, CI matrix over
    both builds.
  - Time estimate +1 week.

CHANGES IN REVISION v2
----------------------
  - No WATCH, and no sharing between any two clients: one live session per
    user. Max-clients limit removed; session claim/release, idle timeout and
    keepalive added.
  - Memory accounting moved from Step 11 to Step 4 (Step 10 quotas needed it).
  - KeyTable (sampleable, SCAN-safe) added in Step 4 instead of discovering
    the need in Steps 5 and 11.
  - SCAN, RENAME, SRANDMEMBER, INFO, CONFIG now assigned to a step.
  - Expiry/eviction DEL logging, frozen expiry during replay, denyoom,
    fd-reuse race, pre-AUTH limits, test caveats (kill -9, DUMP, differential
    nondeterminism), fork rules, benchmark setup, honest time estimate.

HOW TO USE THIS DOCUMENT
------------------------
Do the steps in order. Each step lists:
  BUILD    - the classes / structs / functions to create
  FEATURES - the commands or behaviors to implement
  TEST     - how to check it works before moving on
  DONE WHEN- the exit criterion

Do not start a step until the previous one's "DONE WHEN" is true. Commit to git
at the end of every step. Keep a running notes file for the README.

Time: the step estimates below add up to roughly 13 to 19 weeks of focused
full-time work (v3 added about one week for jemalloc and the A/B steps).
Part-time will be longer; 2 to 4 months was optimistic.

SCOPE (updated, v2)
-------------------
  - Each user has an isolated keyspace (one Database per user). Nothing is
    shared between users.
  - No two clients ever share data: a user has at most ONE live session
    (authenticated connection) at a time; a second AUTH for a busy user is
    refused.
  - Not implemented: WATCH/UNWATCH, Pub/Sub, BLPOP/BRPOP.
  - MULTI/EXEC is optional and simple (it adds no isolation here).
  - Assumption: a user is an account selected by AUTH, with data that
    persists across connections and restarts.
  - Memory allocator: jemalloc is used from the start. glibc is kept as a
    second build only to benchmark against. Same source, one CMake switch.

==============================================================================
STEP 0B: JEMALLOC AS THE ALLOCATOR + A/B HARNESS               (2-3 days)
==============================================================================
BUILD
  - Install jemalloc (libjemalloc-dev) and record its version and your glibc
    version (ldd --version) in the notes file.
  - CMake option ALLOCATOR=jemalloc|glibc, default jemalloc. Use
    find_library or pkg-config. If jemalloc is requested and missing, FAIL the
    configure step with a clear message (no silent fallback to glibc). Define
    REDIS_ALLOC_JEMALLOC or REDIS_ALLOC_GLIBC.
  - Presets: release-jemalloc, release-glibc, asan. The asan preset forces
    glibc and errors out if ALLOCATOR=jemalloc is combined with a sanitizer.
  - src/alloc/alloc_stats.h/.cpp: AllocStats (struct) and free functions
    allocatorName(), allocatorVersion(), readAllocStats(),
    releaseFreeMemory(). Only this module includes <jemalloc/jemalloc.h> or
    <malloc.h>. jemalloc: mallctl (advance "epoch", read stats.allocated,
    stats.active, stats.resident, stats.mapped, stats.retained). glibc:
    mallinfo2() plus VmRSS from /proc/self/status.
  - Startup self-check in main(): print "allocator: jemalloc <version>" or
    "allocator: glibc <version>". The jemalloc build aborts if mallctl("version")
    fails. The glibc build aborts if jemalloc symbols are present (for
    example dlsym(RTLD_DEFAULT, "mallctl") is non-null, which happens when
    someone runs it with LD_PRELOAD=libjemalloc.so). This makes it impossible
    to mislabel a benchmark result.
  - bench/allocator/alloc_micro.cpp: standalone micro-benchmark, no server
    needed. Scenarios:
      (a) allocate and free many small std::string (16-64 bytes),
      (b) mixed sizes 16 B to 4 KB with random lifetimes (churn),
      (c) grow a std::deque and an unordered_map to 1M entries, then free all,
      (d) repeated growth of a std::string / byte buffer (realloc pattern),
      (e) fragmentation: allocate 1M objects, free every other one, refill
          with a different size mix, and compare RSS with live bytes.
  - bench/allocator/run_ab.sh: builds both presets from the same commit, runs
    a given binary and arguments on each, N = 10 runs, alternating order
    (jemalloc, glibc, jemalloc, glibc ...), and writes a CSV with wall time,
    peak RSS, allocator stats and the git commit. Reused later for the server.
FEATURES
  - Same source, two binaries: build/release-jemalloc and build/release-glibc.
TEST
  - Prove which allocator is active: self-check line, ldd/nm on the binaries,
    and MALLOC_CONF=stats_print:true prints a jemalloc stats report at exit
    for the jemalloc build and nothing for the glibc build.
  - Run the glibc binary with LD_PRELOAD=libjemalloc.so: the self-check must
    abort it.
  - Run alloc_micro through run_ab.sh on both builds; save the CSV.
DONE WHEN
  - Both builds compile from one commit, the self-check proves the active
    allocator, and a micro-benchmark baseline (10 runs per scenario per
    allocator, median and spread) is saved in bench/results/allocator_micro/.

==============================================================================
STEP 2: RESP PARSER AND WRITER                                 (3-5 days)
==============================================================================
BUILD
  - Buffer (class): growable byte buffer with read/write positions.
  - RespValue (struct): variant of simple string, error, int, bulk, array, null.
  - RespParser (class): incremental. Returns "need more data", "got a command",
    or "protocol error".
  - RespWriter (class): writeOk, writeError, writeInt, writeBulk, writeNull,
    writeArray header.
FEATURES
  - Parse arrays of bulk strings (what clients send).
  - Parse inline commands (optional, for telnet testing).
  - Handle pipelined commands in one buffer and commands split across reads.
TEST
  - Unit tests: feed the parser one byte at a time, then in random chunks,
    then many commands at once. All must give identical results.
  - Fuzz: random bytes must never crash or hang.
  - Reject oversized lengths (for example bulk > 512 MB, array > 1M), and use
    a much smaller limit (for example 64 KB per command) for connections
    that have not authenticated yet; the user and quota are unknown then.
DONE WHEN
  - Parser passes split-at-every-offset tests and fuzzing under ASan.


==============================================================================
STEP 3: EVENT LOOP + MANY CLIENTS                              (4-6 days)
==============================================================================
BUILD
  - EventLoop (class): epoll_create, epoll_ctl add/mod/del, epoll_wait,
    non-blocking listening socket, timer tick (for example every 100 ms).
  - Connection (struct): Socket, in Buffer, out Buffer, client id,
    flags (close_after_reply), User* user (null until AUTH, see Step 4).
    A struct is enough; add a class only if you need to enforce an invariant
    such as an output-buffer limit.
  - Connection registry: vector<unique_ptr<Connection>> indexed by fd.
  - CommandSpec / CommandContext (structs), CommandTable (class).
  - First handlers as free functions: cmd_ping, cmd_echo, cmd_quit.
FEATURES
  - Accept many clients. Read, parse, dispatch, buffer replies, flush.
  - Register EPOLLOUT only when there is unsent output.
  - TCP_NODELAY, SO_REUSEADDR, handle EAGAIN, EINTR, partial writes, EOF.
  - Unknown command -> -ERR unknown command; wrong arity -> -ERR wrong number
    of arguments.
  - Close connections through ONE function, deferred to the end of the loop
    iteration (or tag connections with a generation id), so a reused fd
    cannot receive a stale event from the previous owner.
TEST
  - 1000 concurrent clients doing PING.
  - redis-benchmark -t ping -c 50 -n 100000, with and without -P 16 pipeline.
  - Repeat that on release-jemalloc and release-glibc through run_ab.sh as a
    first smoke A/B. Expect almost no difference (PING barely allocates); the
    point is to prove the harness works end to end before real workloads exist.
  - A client disconnecting mid-command must not leak or crash.
  - Close a client and accept a new one (same fd) inside one epoll_wait
    batch: the new client must not see the old client's event.
  - Log every command redis-cli (interactive) and redis-benchmark send at
    startup (for example COMMAND DOCS, CONFIG GET) and answer them minimally
    so they do not break; this list feeds the pre-AUTH allow-list in Step 4.
DONE WHEN
  - redis-benchmark runs to completion, no leaks (ASan), fd count returns to
    baseline after clients disconnect.


==============================================================================
STEP 4: USERS, DATABASE + STRINGS                              (4-6 days)
==============================================================================
BUILD
  - ObjType (enum class), Object (struct with std::variant data + access_meta).
  - KeyTable (class): the keyspace hash table. Needs O(1) random sampling
    (Steps 5 and 11) and a rehash-safe SCAN cursor. Decide now: custom table,
    or unordered_map + side vector of keys. Switching later is painful.
  - Database (class): find(), findOrCreate(), erase(), size(), flush().
    ONE INSTANCE PER USER. Tracks used_bytes on every insert/erase/resize
    (moved here from Step 11: quotas in Step 10 need it). Count LOGICAL sizes
    (key bytes + value bytes + fixed per-object overhead), not
    malloc_usable_size(), so quotas and eviction behave identically on the
    jemalloc and glibc builds. Has a removal sink
    (callback) fired when a key is removed by lazy expiry, active expiry or
    eviction, so Step 8 can log DELs.
  - User (struct): { id, name, password hash, Database db, quota,
    session_client_id }. Store an id, not a Connection*, so it cannot dangle.
  - UserRegistry (class): map name -> User, lookup, create (from a users file
    or a config), password verification, claimSession()/releaseSession().
  - CommandContext now carries Database& for the authenticated user. Handlers
    never see other users' data.
  - cmd_auth.cpp: AUTH, WHOAMI.
  - cmd_string.cpp handlers.
  - cmd_keys.cpp: DEL, EXISTS, TYPE, DBSIZE, FLUSHALL, KEYS, SCAN, RENAME.
  - cmd_server.cpp: ECHO, INFO (minimal for now), CONFIG GET (minimal).
    INFO already has a memory section: allocator name/version, used_bytes,
    allocator allocated, allocator resident, process RSS, fragmentation ratio
    (from AllocStats, Step 0B).
FEATURES
  - AUTH <user> <password>: binds the connection to that user's Database and
    claims the user's single session. If the user already has a live session
    -> error, connection stays unauthenticated. Second AUTH on an
    authenticated connection -> error.
  - Before AUTH only AUTH, PING, QUIT (plus whatever redis-cli/redis-benchmark
    need at startup, found in Step 3) are allowed, else -NOAUTH.
  - SET (with EX, PX, NX, XX, KEEPTTL parsing can wait until Step 5),
    GET, INCR, DECR, INCRBY, APPEND, STRLEN, MGET, MSET.
  - WRONGTYPE error helper used by every later type.
  - Integer parsing with overflow detection (INCR on 2^63-1 must error).
TEST
  - Unit tests for each command.
  - Isolation test: users A and B both SET "balance" to different values,
    interleaved from separate connections; each only ever reads its own.
    DEL, KEYS, DBSIZE and FLUSHALL by A leave B untouched.
  - Session test: while A is connected, a second connection doing AUTH A is
    refused and A is undisturbed; after A disconnects, AUTH A succeeds and
    A's data is still there.
  - Differential test script: random SET/GET/INCR/APPEND/DEL sequences against
    real Redis; compare all replies. (Your server needs AUTH, real Redis does
    not: handle that in the harness.) Normalize nondeterminism later when
    sets/hashes/expiry appear: compare unordered replies as sets.
DONE WHEN
  - Differential test of 100k random string operations shows zero differences.


==============================================================================
STEP 5: KEY EXPIRY                                             (3-4 days)
==============================================================================
BUILD
  - ExpiryIndex (class): key -> deadline map, sampling container.
  - Database::find() does the lazy check.
  - Database::activeExpireCycle(time_budget) per user, called from the timer
    tick through UserRegistry::activeExpireCycle(total_budget), which
    round-robins across users (remember where it stopped) so the total stall
    stays within one budget no matter how many users exist.
  - Clock helper: nowMs() (wall-clock ms, so AOF/RDB deadlines stay valid).
    Use std::chrono::steady_clock for ALL latency/stall measurement; wall
    clock can jump.
  - ExpiryIndex needs O(1) random sample and O(1) removal (vector of keys +
    index map, swap-remove).
FEATURES
  - SET ... EX/PX, EXPIRE, PEXPIRE, EXPIREAT, PEXPIREAT, TTL, PTTL, PERSIST.
  - TTL return codes: -2 missing key, -1 no expiry.
  - SET clears TTL unless KEEPTTL.
  - Loading mode: while AOF/RDB is loading, lazy and active expiry are
    disabled (see Step 8), then one full expiry pass runs after load.
  - Active cycle: sample 20 keys, delete expired, repeat while >25 percent
    expired, hard stop at the time budget.
TEST
  - Key with PX 100 is gone after 150 ms, even if never accessed again
    (verifies the active cycle).
  - Insert 1M keys with short TTL, measure the longest event-loop stall while
    they expire. It must stay under your budget.
  - Also measure the stall of DEL on one huge container (for example a set of
    1M members). The active-expiry budget does not cover freeing big values;
    note the result and consider incremental/lazy freeing.
  - Run both stall measurements (1M expiring keys, DEL of a 1M-member set) on
    release-jemalloc AND release-glibc, and record the max stall and the RSS
    after the free for each. Big frees are an allocator workload.
DONE WHEN
  - Expiry is correct (lazy and active) and the max stall is measured and
    recorded for the README.

==============================================================================
STEP 7: SKIP LIST + SORTED SETS                                (1-2 weeks)
==============================================================================
BUILD
  - SkipList (class): private Node { double score; string member;
    levels[] of { forward*, span } }, backward pointer, max level 32,
    promotion probability 0.25.
      insert(score, member), erase(score, member), rank(score, member),
      getByRank(r), rangeByRank(a, b), rangeByScore(min, max), size().
  - ZSet (class): SkipList + unordered_map<string,double>, one add/remove/
    updateScore API that updates both so they cannot diverge.
  - cmd_zset.cpp.
FEATURES
  - ZADD (NX, XX, GT, LT, CH), ZREM, ZSCORE, ZRANK, ZREVRANK, ZCARD,
    ZRANGE (WITHSCORES, REV), ZRANGEBYSCORE, ZINCRBY, ZCOUNT, ZREMRANGEBYRANK.
  - Order: by score, ties by member (lexicographic).
  - Parse +inf, -inf, and exclusive ranges like "(5".
TEST
  - Property test: after random operations, compare SkipList contents with a
    std::set<pair<double,string>> reference.
  - Invariant test: ZSet map size == SkipList size after every operation.
  - Differential test against real Redis.
  - Micro-benchmark: insert 1M members, measure ZADD and ZRANK latency.
DONE WHEN
  - Property and differential tests pass; you can explain span-based rank.


==============================================================================
STEP 7B: ALLOCATOR A/B MEMORY CHECKPOINT                       (2-3 days)
==============================================================================
Why here: all five value types now exist, so memory behavior can be measured
on realistic data before AOF, eviction and optimizations change the picture.
BUILD
  - bench/allocator/mem_profile.sh plus a small load generator (C++ or
    Python, pipelined, one user per process) that fills the server and then
    calls INFO and reads /proc/<pid>/status after each phase.
  - Workloads (same data and seed for both builds):
      W1  1M string keys, 16 B keys, 64 B values
      W2  1M string keys, 256 B and then 1 KB values
      W3  100k hashes with 10 fields each
      W4  100k lists with 100 elements each
      W5  100k sets with 50 members each
      W6  10 sorted sets with 100k members each
      W7  churn: fill 1M keys, then 3 rounds of {overwrite 50 percent with a
          different value size, delete 30 percent, refill}
      W8  free everything (FLUSHALL, DEL on big containers) and check how much
          RSS is handed back to the OS
  - Record after every phase: used_bytes (own accounting), allocator
    allocated, allocator resident, process RSS, fragmentation ratio, and
    bytes per key.
  - Run the same workloads against real Redis (used_memory, used_memory_rss).
TEST
  - Both builds return identical logical data (a type-aware scan matches),
    so the allocator changes nothing observable.
  - used_bytes is within the documented tolerance of the allocator's allocated
    figure on both builds; investigate if not.
DONE WHEN
  - A table (workload x allocator: RSS, fragmentation ratio, bytes/key, RSS
    after free) is saved in bench/results/allocator_mem/, with a short
    written finding. Note any data type that is memory-heavy (for example
    unordered_map nodes) as input for Step 13B compact encodings.


==============================================================================
STEP 8: AOF PERSISTENCE                                        (1-2 weeks)
==============================================================================
BUILD
  - FsyncPolicy (enum class): Always, EverySec, No.
  - AofWriter (class): open in append mode, buffer, flush, fsync by policy.
  - AofLoader (class): read file with RespParser, execute each command via
    the normal dispatcher with replies discarded.
  - Dispatcher hook: after a successful write command, call
    aof.append(user, command). Use CommandSpec flags to know which are writes.
    Never log AUTH (it contains the password).
  - Removal sink: lazy expiry inside a read command (GET), active expiry and
    eviction all delete keys OUTSIDE the write-command hook. Connect the
    Database removal sink to aof.append(user, DEL key) so replay matches.
  - Decide and document the per-user layout: one AOF file per user (simplest)
    or one shared file with "user switch" records. On load, replay each
    record into the correct user's Database.
  - Rewrite relative expiry to absolute before logging.
FEATURES
  - appendonly yes/no, appendfsync always/everysec/no (via Config).
  - Replay on startup, with AOF writing disabled AND expiry frozen during the
    load, then a full expiry pass after it (otherwise a key that expired
    during downtime disappears mid-replay and later INCR/APPEND diverge).
  - Ignore (and truncate) a partial command at the end of the file.
  - Expired and evicted keys log a DEL.
  - BGREWRITEAOF (later in this step or Step 12): fork, dump the dataset as
    commands to a temp file, buffer new writes, append them, rename(). One
    fork covers all users' files; never run it together with BGSAVE.
TEST
  - Write data, restart, verify identical dataset. DUMP is not implemented,
    so compare with a type-aware scan: KEYS + TYPE, then GET / HGETALL /
    LRANGE / SMEMBERS / ZRANGE WITHSCORES for each key, plus PTTL.
  - Crash test: run a client writing continuously, kill -9 the server at a
    random time, restart, verify the dataset is a valid prefix of the writes
    (for "always": nothing acknowledged is lost).
    CAVEAT: kill -9 does not discard bytes already passed to write(), so it
    cannot tell the fsync policies apart; it only loses your user-space
    buffer. To test fsync semantics simulate power loss (VM hard reset,
    dm-flakey, or an LD_PRELOAD shim that drops unsynced writes).
  - Corrupt/truncate the file by hand and check the loader's behavior.
  - Measure throughput for each fsync policy and record it.
DONE WHEN
  - 100 random kill -9 runs recover cleanly, at least one power-loss
    simulation per fsync policy passes, fsync policy numbers recorded.


==============================================================================
STEP 9: TRANSACTIONS (OPTIONAL, NO WATCH)                      (2-3 days)
==============================================================================
BUILD
  - TxState, QueuedCmd (structs), stored inside Connection.
  - cmd_tx.cpp: MULTI, EXEC, DISCARD.
  - Dispatcher change: if in_multi and the command is not
    EXEC/DISCARD/MULTI, queue it and reply +QUEUED.
  - No per-key versions, no WATCH, no Database::touch().
FEATURES
  - EXEC runs the queue back to back and returns an array of replies.
  - EXECABORT if a queueing error occurred.
  - Nested MULTI -> error. EXEC or DISCARD without MULTI -> error.
  - Queue is discarded if the client disconnects.
  - AUTH is never queued; cap queue length/size.
  - Remember in the README: with no WATCH and no sharing, EXEC gives no extra
    isolation; it gives queue-abort semantics and contiguous AOF logging.
  - AOF: log the transaction contiguously.
TEST
  - Syntax error while queueing -> EXECABORT.
  - Runtime error in the middle of EXEC does not stop later commands.
  - A user's transaction only affects that user's Database.
DONE WHEN
  - Behaviors above match real Redis in a side-by-side script.


==============================================================================
STEP 10: PER-USER LIMITS AND ISOLATION HARDENING               (3-5 days)
==============================================================================
BUILD
  - Per-user limits stored in User: memory quota, max output-buffer size per
    connection (check in one queueReply() function; make Connection a class
    now so this and session release are enforced invariants). Quota
    accounting already exists from Step 4; with noeviction a user over quota
    gets -OOM on denyoom commands here, eviction policies arrive in Step 11.
  - Client idle timeout and SO_KEEPALIVE so a dead peer releases its session.
  - Per-user stats: used bytes, key count, commands processed (INFO section).
  - Safe disconnect handling: every close calls releaseSession() exactly once;
    no dangling User* or Database* anywhere.
FEATURES
  - Refuse AUTH for a user that already has a live session (already built in
    Step 4; here harden it: idle timeout, keepalive, release on every close
    path including errors and output-buffer breaches).
  - Disconnect clients that exceed the output-buffer limit.
  - Rate or size limits on a single command (for example max bulk length)
    so one user cannot stall the shared event loop.
  - Optional: password hashing with salt, and a users file loaded at startup.
    Limit failed AUTH attempts per connection. A slow KDF would stall the
    shared loop, so keep it cheap or run it off-thread.
TEST
  - Concurrency/isolation stress test: 20 clients, one user each, run random
    commands for minutes. Each client checks its own expected state
    (a model kept in the test). No cross-user contamination ever. Add extra
    connections that try to AUTH as busy users: all refused, owners
    undisturbed.
  - Kill clients mid-command: no leaks or use-after-free (ASan).
  - One user filling its quota does not affect another user's writes.
DONE WHEN
  - Stress test passes under ASan/UBSan and limits behave as documented.


==============================================================================
STEP 11: EVICTION (LRU / LFU)                                  (1 week)
==============================================================================
BUILD
  - Memory accounting already exists (Step 4); here add the global total and
    enforcement. Eviction samples keys through KeyTable::sample().
  - EvictionPolicy (abstract class): onAccess(obj), pickVictim(db).
  - ApproxLru (class): 24-bit second-resolution clock stored in
    Object::access_meta; samples N keys.
  - ApproxLfu (class): 8-bit log counter + decay timestamp.
  - Config: maxmemory (global), user-maxmemory (per-user quota),
    maxmemory_policy, maxmemory_samples.
  - Hook: before executing a command flagged denyoom, if the user's
    used_bytes exceeds the user's quota, evict from that user's Database
    until under the limit, or return -OOM (noeviction or no victim). DEL and
    other shrinking commands are never refused. A user at quota never evicts
    another user's keys.
  - At startup/user creation require sum(user quotas) <= maxmemory, so the
    global limit never triggers before a user's own quota (otherwise a tiny
    user gets -OOM because of other users).
FEATURES
  - Policies: noeviction, allkeys-lru, volatile-lru, allkeys-lfu, volatile-lfu.
  - Update access_meta on every key read/write (cheap).
  - Evictions logged to AOF as DEL, through the Database removal sink.
TEST
  - Fill to maxmemory with a skewed access pattern (hot 20 percent of keys);
    check the hot keys survive more often under LRU/LFU than random eviction.
  - Experiment: vary sample size (3, 5, 10) and plot hit rate vs sample size.
    This graph is great README material.
  - Allocator angle: run the fill-to-maxmemory test with a mixed-size churn
    on both builds and record RSS versus maxmemory over time. Eviction bounds
    used_bytes, not RSS; the fragmentation ratio shows how far RSS overshoots
    on each allocator.
DONE WHEN
  - Memory stays near the limit under load; hit-rate experiment recorded.

STEP 13: BENCHMARKS, PROFILING, OPTIMIZATION                   (3-4 weeks)
==============================================================================
13A. ALLOCATOR A/B BENCHMARK  (jemalloc vs glibc)
-------------------------------------------------
Contenders (three rows in every table):
  1. your server + jemalloc   (build/release-jemalloc)
  2. your server + glibc      (build/release-glibc)
  3. real Redis (note its allocator from INFO memory: mem_allocator; if you can
     build it with MALLOC=libc add a fourth row)
Both of your builds come from the SAME commit with identical flags and config.

Environment control (record all of it in the results folder):
  - Pin the server and the load generators to different cores (taskset).
  - CPU governor "performance"; note turbo on/off.
  - Same machine, nothing else running. Loopback is fine, but say so.
  - Transparent huge pages: record /sys/kernel/mm/transparent_hugepage/enabled
    and run with the same setting for every contender (THP strongly affects
    RSS and allocator behavior).
  - Fresh server start per run, warm-up phase discarded, same dataset and seed.
  - Save lscpu, kernel version, glibc version, jemalloc version, MALLOC_CONF,
    and the git commit next to every result.

Workloads (each on every contender):
  W-A  GET/SET mix 90/10 and 50/50, payloads 16 B, 256 B, 4 KB, pipeline 1 and
       16. With one session per user, use N processes of -c 1, one user each,
       N in {1, 4, 16}. Same N for real Redis.
  W-B  Type-heavy: HSET/HGET, LPUSH/LRANGE, SADD/SISMEMBER, ZADD/ZRANK on a
       1M-member sorted set.
  W-C  Churn soak (30 to 60 minutes): mixed value sizes, TTLs, overwrites and
       eviction at maxmemory. Sample RSS, used_bytes and fragmentation ratio
       every 10 seconds. Graph RSS and fragmentation versus time.
  W-D  Big free: DEL / UNLINK of a 1M-member set and FLUSHALL. Record the
       longest event-loop stall and the RSS afterward.
  W-E  Persistence interaction: BGSAVE and BGREWRITEAOF while writing. Record
       fork stall, client latency during the child, and child COW growth.
  W-F  Expiry storm: 1M keys expiring at the same moment. Record the longest
       stall.

Metrics:
  - Throughput (ops/s); latency p50 / p99 / p99.9 / max from a histogram
    (HdrHistogram), not averages.
  - Steady and peak RSS, fragmentation ratio, bytes per key.
  - page-faults and minor-faults (perf stat), cache-misses, and the share of
    CPU time spent in malloc/free (jemalloc je_* or arena functions, glibc
    _int_malloc/_int_free) from perf record.
  - Allocation counts (jemalloc stats nmalloc/ndalloc; for glibc use a perf
    uprobe on malloc or ltrace on a short run).

Statistics and fairness:
  - At least 10 runs per cell (at least 5 for the soak), alternating the
    order of the contenders each round to cancel drift (thermal, cache, page
    cache).
  - Report the median plus min/max (or a confidence interval). If the
    difference is within run-to-run noise, write "no measurable difference".
    Never report a single run.
  - Tuning sweep AFTER the default-settings baseline, one knob at a time:
      jemalloc: dirty_decay_ms (0, 1000, default), muzzy_decay_ms, narenas
                (1 vs default), background_thread (false/true), tcache.
      glibc   : MALLOC_ARENA_MAX=1, MALLOC_MMAP_THRESHOLD_,
                MALLOC_TRIM_THRESHOLD_, and malloc_trim(0) from serverCron
                after large frees.
    Report defaults AND best-tuned for BOTH allocators, so glibc is not
    compared in an untuned state against a tuned jemalloc.
  - Do the 13B optimizations on the jemalloc build first. At the end re-run
    the final build on glibc as well and mark which gains depend on the
    allocator (arena/pool allocators and string-copy removal are the likely
    ones).

Scripts and output:
  - bench/allocator/run_matrix.sh loops over builds x workloads x runs and
    writes CSV; bench/allocator/plot.py draws the graphs. Results go to
    bench/results/allocator/<date>/.

DONE WHEN (13A)
  - You have: a throughput + latency percentile table, an RSS/fragmentation
    versus time graph, and the big-free / fork / expiry stall table, for both
    allocators and real Redis, plus a written conclusion saying which
    allocator is the default and why, backed by the numbers (including
    "no significant difference, kept jemalloc because ...").

13B. GENERAL BENCHMARKS, PROFILING, OPTIMIZATION
------------------------------------------------
BUILD / DO
  - Scripts that run redis-benchmark against real Redis and your server with
    identical settings (clients, pipeline depth, payload size, command mix).
    One session per user means a single "redis-benchmark --user X -c 50" is
    refused: generate N users and run N benchmark processes with -c 1 each,
    and do the same against real Redis for fairness. PING needs no AUTH.
  - Latency measurement: p50, p99, p99.9 (use a histogram, for example
    HdrHistogram), not just averages.
  - perf record + flamegraphs; identify the top 3 hot spots.
  - Try and measure (one change at a time, before/after table):
      * custom open-addressing hash table for the keyspace
      * arena or pool allocator for Connection objects and small strings
        (measure on top of jemalloc; its thread cache already makes small
        allocations cheap, so expect a smaller gain than against glibc)
      * small-string optimization / avoiding std::string copies
        (use string_view and move semantics)
      * batching writes with writev, reducing epoll_ctl calls
      * prefetching hash buckets for pipelined commands
      * compact encodings for small hashes/lists/sets (listpack-style)
      * optional I/O threads for read/write while keeping execution
        single-threaded
  - Check cache behavior (perf stat: cache-misses, branch-misses).
DONE WHEN
  - You have a table of optimizations with measured gains, and honest numbers
    versus real Redis (even if you are slower, explain why). The 13A allocator
    comparison is finished and its conclusion is written down.

STEP 14: OPTIONAL EXTENSIONS (pick one or two)
==============================================================================
  - Replication: REPLICAOF, full sync (RDB transfer), command stream,
    replication backlog, partial resync (PSYNC).
  - Streams: XADD, XRANGE, XREAD, consumer groups (market-data style).
  - Multi-threaded sharded design: pin each user to one thread, so no locks
    are needed because users share nothing. Write a tradeoff comparison
    against the single-threaded version (a hot single user is limited to one
    core; many users scale with cores). This is the best extension for this
    scope. Caveat: fork()-based BGSAVE/BGREWRITEAOF is unsafe with several
    mutating threads (the child can capture a half-finished update), so this
    extension needs per-shard, non-fork snapshotting. Session claim and
    handing a connection to its user's thread after AUTH become cross-thread
    operations. Re-run the allocator A/B (Step 13A) here: arena contention
    across threads is where jemalloc and glibc differ the most.
  - Lua-free scripting alternative, or a simple module/command plug-in API.
  - HyperLogLog, bitmaps, geo commands.
